# 内核功耗与性能验证

## Overview

手机上测功耗和性能，**最大的风险不是测错，是从噪声里读出结论**。

跑三次取平均，发现新内核「省电 2%」，实际那 2% 完全在噪声里。所以本 skill 的判据不是「测出来是多少」，而是：

> **这个差异，比这台设备的测量噪声大吗？**

配套工具 `scripts/ab-stats.py` 把这个判断变成一个数字。

## When to Use

- 要判断新内核是否真的省电 / 更快 / 更稳。
- 换了个 tunable，想知道有没有效果。
- 已经测了，但两次结论不一致。
- 要向别人（或自己）证明改动有效。

**何时不用**：内核还没刷上去并验证过（先去 `safe-kernel-flash`）。

## 第一步：先量噪声地板，再谈结论

同一内核、同一条件，连续测 **3 次以上**，算 `CV = std / mean`。

**CV 就是这台设备的噪声地板。** 后面所有判据都相对它。

```bash
python3 scripts/ab-stats.py --a stock.txt --b modded.txt --metric energy
```

**判定顺序（不能颠倒）**：

1. **先看置信区间。** bootstrap 95% CI 跨过 1.0 → 判「测不出来」，到此为止。
2. **CI 排除 1.0** 才算有统计证据，再按阈值给结论。
3. **最后才看幅度。** 若此时同时满足 `|Δ| < 2 × CV`，说明效应贴着噪声地板——CI 虽然排除了 1.0，也只判「暂时通过」，必须再独立复测一轮才算数。

> 把第 3 步提到第 1 步，是这套方法论最容易犯的错：先拿 `2×CV` 否掉结论，会把一个已经被 CI 证实的真实小效应误判成「测不出来」。`ab-stats.py` 的早期版本就是这么写的，现在顺序已写死在脚本里。

CV=2% 的设备上，一次测量报出「省电 1.5%」——**如果 CI 跨 1.0**，那是在描述随机数；**如果 CI 排除 1.0 且两端是交叉配对的**，那是一个真实但微弱、必须复测的效应。这两种情况不能混为一谈。

## 证据层级：哪些数字可信

| 层级 | 来源 | 可信度 |
| --- | --- | --- |
| 1 | `/sys/class/powercap/*/energy_uj` | **唯一真正的焦耳来源**。有它就以它为准 |
| 2 | `/sys/devices/system/cpu/cpufreq/policy*/stats/time_in_state` 频率驻留差分 | 只能说明「频率低了」，不等于「省电了」 |
| 3 | 夜间待机真实放电 mA | 变量最少的窗口，需要自动飞行、灭屏 |
| 4 | `dumpsys batterystats` | 框架**估算值**，仅作交叉校验 |

三者冲突时的信任顺序：**能量计数器 > 电池电流 > batterystats**。

**物理上限（不要假装能绕过）**：电池电流有 3–4 mA 量化噪声，短负载根本测不出功耗差异。只有**≥1 小时持续负载**或**整夜待机**才有统计意义。

若内核没开 `CONFIG_POWERCAP`，方案退化为「电池电流 + 温度 + 频率驻留」三件套，灵敏度显著下降——**这时更应该直说测不出来**。

## 第二步：A/B 协议（协议错了，统计再漂亮也没用）

**唯一自变量是内核镜像。** 两端必须满足：

- 同一 vendor 分区、同一 system 版本
- 同一 root 模块集、同一已装 App 集
- **记录并比较两端的 tunable**（governor、sched 参数）

**必须交叉配对：A B A B A B ……，禁止 A×5 再 B×5。** 顺序测量测的是**温度漂移**，不是内核差异——这是手机 A/B 测试最常见的致命错误。

其余固定项：先热身两轮；固定亮度与刷新率；关自适应电池与自适应刷新；两端网络状态一致；记录室温。

**分两个结论**：

1. 把 tunable 拉平后比 → 测的是**内核本身**。
2. 各自默认值比 → 测的是**实际体验**。

两个结论可能相反，这很正常，但要分别说清楚。

## 第三步：算，不要看

```bash
# 每组每行一个测量值
python3 scripts/ab-stats.py --a stock-energy.txt --b modded-energy.txt \
    --metric energy --target-delta 0.03
```

它输出：CV、比值点估计、**bootstrap 95% 置信区间**、按阈值给出的判定，以及「想分辨 Δ 需要每臂多少次」。

**判据看置信区间是否跨 1.0，而不是 p 值。**

样本量：`n/臂 ≈ 15.7 × (CV/Δ)²`。CV=2% 想分辨 2% 的差异，每臂要 16 次；想分辨 5%，2–3 次就够。**这不是可以省的一步**——样本量不够时，任何结论都是噪声的别名。

## 第四步：按类别判定

| 目标 | 通过标准 |
| --- | --- |
| **省电** | `E_uj/work` 比值 ≤0.97 且 CI 上界 <1.0；0.97–1.03 判「无差异」；>1.03 判更费电 |
| **夜间待机** | 真实放电 mA 低 ≥5%，且电池温升不 ≥0.5°C |
| **更快** | 吞吐 ≥2% 提升且 CI 下界 >0；p99 延迟劣化 ≤5%；p99.9 wakeup 延迟劣化 ≤10% |
| **更流畅** | Janky frames % 不高于原厂 |
| **更稳** | **72h 零 panic/watchdog/hard lockup/异常重启 + 20 轮子系统回归全过** |

**稳定性没有「平均而言」**：出现任意一次 panic，直接判失败。一次 panic 就意味着有用户会遇到。

稳定性取证（首选现场是 pstore，不是 dmesg）：

```bash
cat /sys/fs/pstore/console-ramoops-0          # 崩溃现场，首选
dmesg | grep -iE 'panic|watchdog|soft lockup|hard LOCKUP|hung task|BUG:|Oops'
cat /proc/sys/kernel/tainted
cmd bootstat print
cat /sys/power/suspend_stats/{success,fail}
```

子系统回归 20 轮：WiFi、移动数据、蓝牙、相机、快充、音频、指纹、传感器、GPU。

## 分两阶段，别一上来就测 72 小时

| 阶段 | 规模 | 何时进入下一阶段 |
| --- | --- | --- |
| Quick screen | 每端 5 次配对，`|Δ|` 足够大才继续 | `|Δ| > 10%` 或效应显著 |
| Confirm | 每端 12–16 次配对 + ≥4h 熄屏待机 + 72h 挂机 | —— |

## Common Mistakes

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 顺序测 A×5 再 B×5 | 测的是温度漂移 | 交叉配对 A B A B |
| 不量 CV 就下结论 | 把噪声当效应 | 先测噪声地板；CI 跨 1.0 就认输，CI 不跨但 `\|Δ\| < 2×CV` 只说「暂时」 |
| 用 p 值当判据 | 忽略了效应量 | 看比值 CI 是否跨 1.0 |
| 拿绝对值比功耗 | 手机绝对功耗不可复现 | 全程比值 |
| 短负载测功耗 | 电流量化噪声吃掉效应 | 长负载或待机窗口 |
| 只看 dmesg 查稳定性 | 崩溃可能没写进 dmesg | 先看 `/sys/fs/pstore/` |
| 两端 tunable 不同还比 | 测的是配置差异不是内核 | 记录并分两种结论 |
| 出现一次 panic 仍说「基本稳定」 | 稳定性不是平均值 | 一次即失败 |

## Real-World Impact

基线里 agent 的方法论已经相当好（比值法、交叉配对、bootstrap CI、`|Δ| < 2×CV` 就认输），甚至主动承认「短负载测不出功耗，不假装能绕过」。**但它对这台设备没有任何专有知识**：`/sys/class/powercap/`、`energy_model`、`thermal_message/sconfig` 这些路径是否存在，必须到真机上裸探。这也是本仓库把「先探测再写」当成通用原则的原因——无论哪一个 skill，**设备是权威，文档是二手**。
